# 使用摩擦清单：minihost / preview

> 来源：一次真实任务里的实际绕路记录（插件真渲染自检），不是设想。
> 每条给「现象 / 证据 / 影响 / 建议」，供决定是否改。**核对过源码，已剔除两条最初误判**（见 §四）。

## 一、结论先看

| # | 缺口 | 类型 | 建议优先级 |
|---|---|---|---|
| 1 | 工具层不传 `env` | 能力不对等（core 已支持） | P1 |
| 2 | 工具层不暴露 `force` | 能力不对等（core 已支持，且提示里让人传） | P1 |
| 3 | 工具层没有 `preview` | 能力不对等（CLI 有） | P1 |
| 4 | `stop` 不支持全停、台账不标归属 | 可清理性 | P2 |
| 5 | `preview gen` 默认产物写进插件仓库 | 默认值方向 | P3 |
| 6 | `preview gen` 的 spec 只能是文件路径 | 便利性 | P3 |
| 7 | 没有「取一个可用 chrome 启动命令」的探测 | 缺能力 | P3（做浏览器门禁时才卡） |

## 二、逐条

### 1 工具层不传 `env`

- **现象**：想给 mini 宿主换数据根（例如把插件数据目录指到临时路径做隔离验证），工具参数里没有 `env`。
- **证据**：`lib/shared/minihost/index.js` 的 `parameters` 只有 `action/plugin/port/path/method/body/services`；分派处 `minihostStart({ plugin, port, services })` 不带 env。而 core 已支持：`lib/core/minihost/tools.js` 里 `const extraEnv = normalizeEnv(args.env)`（接受对象或 JSON 字符串），并合并进 `childEnv`。
- **影响**：只能绕开工具直接 `node lib/core/minihost/host.mjs`——**正确做法要绕路**，于是各人各写一套，隔离形同虚设。
- **建议**：`parameters` 加 `env`（对象或 `KEY=VALUE` 字符串），分派时原样传给 `minihostStart`。

### 2 工具层不暴露 `force`

- **现象**：同参数重复 start 时，core 返回的提示让人「传 `force:true` 自动重启」，但工具层没有这个参数。
- **证据**：`lib/core/minihost/tools.js:94` 有 `if (args.force === true) { … }`，提示文案在 `:103`；`lib/shared/minihost/index.js` 的 schema 无 `force`。
- **影响**：**提示与可达能力不一致**——用户照着提示传，参数会被丢弃，行为不变，容易误判成「force 没生效」。
- **建议**：schema 加 `force: boolean` 并透传；或提示文案改为「（工具层暂不支持 force，请先 stop）」。

### 3 工具层没有 `preview`

- **现象**：minihost CLI 支持 `--preview <html>`（让根路径 `/` 直接返回预览页），工具层无法指定。
- **证据**：`lib/core/minihost/host.mjs:10,16,58` 有 `--preview`；`lib/core/minihost/tools.js:130-135` 的 `spawnArgs` 只拼 `--plugin/--port/--services/--deps`。
- **影响**：要做「同一个进程里既有真后端又有真前端页面」，只能 CLI 起，或另起 preview 服务再手工配 `--backend`（两进程、两处清理）。
- **建议**：工具加 `preview`（HTML 路径），透传成 `--preview`。

### 4 `stop` 不支持全停、台账不标归属

- **现象**：`stop` 只能按 `port` 或 `plugin`；多会话/多人共用一台机器时，`list` 看不出哪个实例是自己起的。
- **证据**：`lib/shared/minihost/index.js:32` `minihostStop({ port, plugin })`；`lib/shared/preview/index.js:33` `stopPreview({ port, file })`。台账项只有 `pid/plugin/port/services/log/startedAt`。
- **影响**：清理孤儿只能 `ps | grep minihost` 反查端口，无法判断能不能杀（误杀别人的实例）。
- **建议**：`stop` 支持 `all`；台账加「启动者标识」（如宿主进程 pid 或会话 id），`list` 默认只列本进程起的，`all:true` 才列全部。

### 5 `preview gen` 默认产物写进插件仓库

- **现象**：不传 `out` 时产物落 `assets/preview.html`，即插件源码目录。
- **证据**：`lib/core/preview/gen.js:119` `const outRel = String(opts.out || spec.output || 'assets/preview.html')`；同文件 `:123` 已有「产物入库提示」（会读 `.gitignore` 判断是否被忽略）。
- **影响**：默认值把「可能被误提交的大文件」放在仓库里。已经做了警告，说明风险是已知的；但**安全的一侧应当是临时目录**，写进仓库应是显式选择。
- **建议**：默认改临时目录（如系统 tmp 下的 `preview-<port>.html`）；`out` 显式给才写仓库，并保留现有警告。

### 6 `preview gen` 的 spec 只能是文件路径

- **现象**：没有 `assets/preview.spec.mjs` 的插件，要先造一个文件才能预览。
- **证据**：`lib/core/preview/gen.js:83` 只按路径解析（缺省 `<plugin>/assets/preview.spec.mjs`）。
- **影响**：一次性验证也要往仓库里塞文件；用完删/不删都别扭。
- **建议**：`spec` 接受 inline JSON（或 `-` 表示从 stdin/参数读），文件路径保持兼容。

### 7 没有「取一个可用 chrome 启动命令」的探测

- **现象**：要做浏览器自动化门禁时，得自己找内核、自己找用户态库、自己拼启动参数。
- **证据**：本机现状是 `DSH_HOME/browser-wrapper.sh` + 独立内核目录 + 一批 `.so`（直接跑内核会缺 `libatk-1.0.so.0`）。这些都在仓库外，工具层没有任何探测入口。
- **影响**：每个想写浏览器门禁的人都要重新踩一遍库缺失；写死的路径换机即失效。
- **建议**：加一个探测能力（如 `browser_probe`），返回可用内核路径 + 需要的环境变量；探不到要**明确报原因**，不要静默返回空。注意与 browser-service 的 CDP 鉴权端点分开，避免与人工浏览互相干扰。

## 三、不是缺口（已核对，纠正误判）

| 曾以为缺 | 实际 | 依据 |
|---|---|---|
| `start` 不返回 pid | **已返回** | `lib/core/minihost/tools.js:148` 起 `{ pid, plugin, port, services, startedAt, log }` |
| 没有子进程日志路径 | **已返回 `log`**，且默认落 `minihost-<port>.log` | 同处 `log: logFile`；`:111-113` 打开该文件作为 stdout/stderr |
| 完全没有数据隔离 | **DSH_HOME 已自动隔离**到 `home-<port>`，并自动注入 `--deps`；core 还支持 `args.env` | `lib/core/minihost/tools.js:119-137` |

> 这三条更正很重要：说明核心层比工具层完整，**缺口主要在「工具层没有把 core 的能力暴露出来」**，而不是功能没实现。

## 四、结构性观察

工具层是 core/CLI 的**子集**，且没有声明差集。表现是：

- 同一个能力，CLI 有、工具没有（`--preview`、`force`）；
- 同一条提示，指向工具层传不进去的参数（`force:true`）；
- 同一种隔离，core 自动做、工具不暴露开关（`env`）。

**低成本改进**：让 `useful_tools help` 同时输出「core/CLI 支持、工具层未暴露」的参数差集。哪怕一个功能都不加，也能让人一眼看出该绕哪条路，而不是各自试错。
