# 机制说明

本文汇总本插件各工具的实现机制、边界与已知限制。README 只讲怎么用，本文讲为什么这么设计。

## 一、读/写观测门禁（mark_read / mark_edit）

宿主的 `write` / `edit` 有一道门禁：**改之前必须读过**。台账按会话记账，每项记录目标文件与其版本；
写入时用 CAS 比对版本，对不上就报 `file changed since it was read`。

版本串由设备号、inode、大小、mtime、ctime 组成。CIFS/SMB 上 mtime/ctime 会「晚到」——
文件写完后时间戳还会再变一次（观测到 3ms 内 `mtime …223135 → …226020`，内容未变）。
宿主在 rename 之后立刻取版本并补发观测，记下的是稳定前的值；下一次写改时磁盘已是稳定值，
CAS 对不上，于是报 stale。这同时解释了「连续编辑」为何也要求重读：`write → edit ✓ → edit ✗`；
同一流程在本地盘连编 3 次全过。`read` 之所以有效，是因为它在时间戳稳定之后才取版本。

两个工具用同一条官方通道（`fs/observed` + 现取 version）补上这个缺口：

- `mark_read` 补「读」：配置读命令集合（落盘 `config.json` 的 `observeTools`），钩子每次现读配置，
  集合里的命令执行后把它读过的文件补发观测。支持宿主工具与 bash 命令两条路径；bash 分支既解析文件参数
  （含 `cat < f` 重定向输入），也解析输出里的 `路径:行号:` 命中行——否则 `grep -rn pat 目录` 只拿到目录、
  里面的文件一个都标不上。跨平台别名归一：`Get-Content`/`gc`/`type`/`more` → cat，
  `Select-String`/`sls`/`findstr` → grep。
- `mark_edit` 补「写」：缺省开启、全局生效。所有经 `write`/`edit` 改过的文件，写完后延迟 `editSettleMs`
  （缺省 1100ms）分三次复核（首次 + 500ms + 1300ms），每次都用当时版本补发，最后一次即稳定值。
  另外解析 bash 写命令（`> >> tee sed -i cp mv touch truncate dd of=`）的目标文件，同样补发。

边界：

- 观测有效到「文件版本再变」为止；文件被任何一方改动后需重新标记。
- 宿主 read 带 offset/limit 只看几行也算读过，把 grep 纳入与宿主自身尺度一致。
- 集合外的命令（`python3 -c`、`node -e` 等，路径常在代码字符串里）不解析，不猜。
- bash 的 `xargs`、`$(...)`、`for` 循环里的文件参数属启发式解析，提取不到。
- 单次钩子调用最多标记 40 个文件（防全仓 grep 观测风暴）。
- `mark_edit` 不读文件内容，它声明的是「这份文件现在是什么」；内容不是自己写的文件仍应老实 `read`。

## 二、github_mirror 为何改 git 层

DSH 从 GitHub 安装插件走 `pnpm add <git spec>` → git clone，`github:owner/repo` 与仓库 URL
被判定为 git 类型，**不经过 npm 源**。界面的「安装源」下拉通过 pnpm `--registry` 传递，只影响 npm 包。
pnpm 的父环境经过清洗（剔除敏感键与 DSH_ 前缀变量），环境变量注入不可靠；HOME 保留，
因此全局 git 配置是唯一稳定的落点。

做法：写 `url.<代理><host>/.insteadOf <host>/`，之后任何 `git clone https://github.com/...`
都被无痕重写到代理，原始地址不用改。

候选清单外置在 `lib/core/github-mirror/candidates.json`，随仓库入库：

```json
{
  "version": 1,
  "candidates": [
    { "mirror": "https://example.invalid/", "hosts": ["github.com"], "disabled": false,
      "failures": 0, "lastOkAt": null, "lastError": null, "lastCheckedAt": null }
  ]
}
```

- `mirror` 必须以 `/` 结尾，工具会自动补齐。
- 显式传入的代理地址自动并入清单；探测成功清零失败计数，失败累加，满 3 次置 `disabled`，`probe` 可恢复。
- `clear` 只删指向受管站点（默认 `github.com`）的 insteadOf 规则，不动其它 git 配置。

## 三、minihost 与 preview 的模拟链路

`minihost` 是后端模拟，`preview` 是前端模拟，通过 `serve` 的 `backend` 参数串成一条链路，
全程不碰真实后端。`backend` 也可指向真实后端，此时是「前端模拟 + 真实后端」。

实现要点：

- **路由匹配只看路径**：`/api/x?y=1` 按 `/api/x` 匹配，query 原样交给 handler。
  早期实现拿含 query 的完整 URL 比对，任何带参数的接口都会 404。
- **默认隔离 DSH_HOME**：子进程的 `DSH_HOME` 指向 `.minihost/home-<port>`，避免插件写脏真实会话与附件库；
  依赖解析用 `--deps` 补回真实 profile 的 node_modules。需要贴近真实环境时用 `env` 覆盖。
- **服务注入**：插件接线依赖 `storageDomain` / `sessions` 等真实服务时，用 `services` 指向一个模块，
  该模块默认导出服务对象或返回服务对象的函数，注入项覆盖同名默认服务。
- 内置宽容桩：`webServer` / `tools` / `storageDomain` / `sessions`，只保证调用不报错、不返回真实数据。
- 预览页内置错误面板：捕获运行时错误与未处理的 Promise 拒绝，渲染在页面顶部。
- `serve` 省略 `backend` 时沿用台账里最近一次存活的 minihost 实例，并在返回值里给出 `backendSource`；
  自动接入也要可追溯，避免静默连错实例。

## 四、ui_check 的能力边界

解析 `lib/client.js` 的 React 元素调用，产出 HTML 骨架页与 JSON 控件清单。

| 问题 | 能否回答 |
| --- | --- |
| 代码里声明了哪些控件、层级、className、文本 | 能，带来源行号 |
| 哪个插槽注册了、渲染的是哪个组件 | 能；组件在文件内定义时还会展开该组件的 UI |
| 条件分支 / 逻辑与里的元素 | 能，收进 `conditional` 子树，不漏报 |
| 运行时到底渲染出来没有（TDZ、条件为 false、hooks 报错、map 空数组） | 不能 |
| 真实外观（主题 CSS 变量、宿主布局约束） | 不能，只能用内联样式近似 |

它是静态骨架，不是渲染检查。清单里控件的 `visible` 恒为 `null`，留给将来的渲染探针填
true/false——两者共用同一份格式，可直接 diff 出「声明了但没渲染」的控件。

## 五、verify_plugin 的六段诊断

| 症状 | 检查段 | 判定依据 |
| --- | --- | --- |
| 装了但不激活、apply 没执行 | `activation` | profile 的依赖、bundle 列表、离线组合出的 loader 行，缺哪项报哪项 |
| 服务拿不到、路由 404 | `inject` | 声明的服务名与安装里实际存在的比对，拼错给近似建议 |
| import 失败、依赖找不到 | `deps` | 在目标 profile 的 node_modules 与 Node 解析里逐个试；`file:` 路径失效单独报 |
| UI 空白、控件没出来 | `client` + `ui` | 有 `dsh.client` 就必须有 `lib/client.js` 且走模块加载器；骨架 controls=0 直接判失败 |
| 改了代码没生效 | `hmr` | 读 profile 的 hmr 配置，判断插件路径是否在 watch 范围 |
| 同步后宿主读不到 | `sync_plugin` 的 `permissions` / `readable` | 写盘后对齐权限与属主，再逐个检查可读 |

激活诊断是离线组合（profile 的 patch 加上各 bundle 的 patch），不启动宿主；
运行期真实装配仍以宿主日志为准。工具本身只做静态分析，不 import 被验证插件。

## 六、DSH 插件规则（9 条）

规则有独立实现，判定口径与提交审计一致：

| 规则 | 严重度 | 判定 |
| --- | --- | --- |
| `dsh/import-bare-cordis` | error | 裸名导入 cordis |
| `dsh/import-bare-schemastery` | error | 裸名导入 schemastery |
| `dsh/tool-render-empty-body` | error | render 空实现或返回 null/undefined |
| `dsh/client-node-builtin-require` | error | client 半部 require Node 内置模块 |
| `dsh/schema-secret-field-role` | warning | token/secret/apiKey 字段缺 `role('secret')` |
| `dsh/patch-insert-unique-id` | warning | insert 行 id 与按 id 覆盖行重复 |
| `dsh/client-module-loader-id` | warning | client 入口未走模块加载器 |
| `dsh/ctx-undeclared-property-read` | blocker | 读 ctx 上未注入属性（注释行豁免） |
| `dsh/host-api-guessed-fallback-chain` | error | 用猜测的 API 兜底链 |

匹配前先遮蔽注释与字符串内容（保持行号不变），只对真实代码匹配——
否则规则说明里写出的违规写法会触发规则自身。需要字符串内容的规则（模块名类）
先确认结构再回原文核对模块名。规则定义文件本身不参与扫描。

## 七、patch_cifs_write 改了什么

CIFS/SMB 不实现 POSIX chmod。官方原子写入流程是
`mkdir 临时目录 → chmod → open → chmod → write → fsync → (可选) chmod → rename`，
第二步就抛 `EPERM`，文件其实还没写进去。

补丁把三处 chmod 包成「尽力而为」：只吞 EPERM / ENOTSUP / EOPNOTSUPP，
EACCES / ENOENT / EIO 等照常抛；rename 与原子性完全不动。

- 补丁目标是套件安装目录，宿主升级会覆盖，升级后重跑 `apply` 即可（幂等）。
- 打完需重启宿主才生效（模块已在进程缓存里）。
- `revert` 从最新备份还原。

## 八、test_env 环境根优先级

参数 `root` > 环境变量 `DSH_TEST_ENV_ROOT` > 插件配置 `config.json` 的 `testEnvRoot` >
按 `DSH_WORKSPACE` / `DSH_HOME` 上一级的「工作区」推算。不写死路径，部署方按配置决定位置。

## 九、quick_command 的执行细节

- 定义存 `<DSH_HOME>/useful-tools/quick-commands.json`，无内置预置，文件不存在时是空表。
- `run` 只执行已定义的命令；同时传 `command` 时先写入 JSON（新增或更新）再执行，不是临时执行。
- `cwd` 缺省空 = 沿用宿主进程的 cwd（不一定是当前工作区）；传了会校验存在且是目录并解析成绝对路径。
- 执行走 `bash -c`（Windows `cmd /c`），默认超时 60 秒，stdout/stderr 各截断 20000 字符。
