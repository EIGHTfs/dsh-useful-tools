# 机制说明

本文汇总本插件各工具的实现机制、边界与已知限制。README 只讲怎么用，本文讲为什么这么设计。

## 一、读/写观测门禁（mark_read / mark_edit）

宿主的 `write` / `edit` 有一道门禁：**改之前必须读过**。台账按会话记账，每项记录目标文件与其版本；
写入时用 CAS 比对版本，对不上就报 `file changed since it was read`。

版本串由设备号、inode、大小、mtime、ctime 组成。CIFS/SMB 上 mtime/ctime 会「晚到」——
文件写完后时间戳还会再变一次（观测到 3ms 内 `mtime …223135 → …226020`，内容未变）。
宿主在 rename 之后立刻取版本并补发观测，记下的是稳定前的值；下一次写改时磁盘已是稳定值，
CAS 对不上，于是报 stale。这同时解释了「连续编辑」为何也要求重读：`write → edit ✓ → edit ✗`；
同一流程在本地盘连编 3 次全过。`read` 之所以有效，是因为它在时间戳稳定之后才取版本。

两个工具用同一条官方通道（`fs/observed` + 现取 version）补上这个缺口：

- `mark_read` 补「读」：配置读命令集合（落盘 `config.json` 的 `observeTools`），钩子每次现读配置，
  集合里的命令执行后把它读过的文件补发观测。支持宿主工具与 bash 命令两条路径；bash 分支既解析文件参数
  （含 `cat < f` 重定向输入），也解析输出里的 `路径:行号:` 命中行——否则 `grep -rn pat 目录` 只拿到目录、
  里面的文件一个都标不上。跨平台别名归一：`Get-Content`/`gc`/`type`/`more` → cat，
  `Select-String`/`sls`/`findstr` → grep。
- `mark_edit` 补「写」：缺省开启、全局生效。所有经 `write`/`edit` 改过的文件，写完后延迟 `editSettleMs`
  （缺省 1100ms）分三次复核（首次 + 500ms + 1300ms），每次都用当时版本补发，最后一次即稳定值。
  另外解析 bash 写命令（`> >> tee sed -i cp mv touch truncate dd of=`）的目标文件，同样补发。

边界：

- 观测有效到「文件版本再变」为止；文件被任何一方改动后需重新标记。
- 宿主 read 带 offset/limit 只看几行也算读过，把 grep 纳入与宿主自身尺度一致。
- 集合外的命令（`python3 -c`、`node -e` 等，路径常在代码字符串里）不解析，不猜。
- bash 的 `xargs`、`$(...)`、`for` 循环里的文件参数属启发式解析，提取不到。
- 单次钩子调用最多标记 40 个文件（防全仓 grep 观测风暴）。
- `mark_edit` 不读文件内容，它声明的是「这份文件现在是什么」；内容不是自己写的文件仍应老实 `read`。

## 二、github_mirror 为何改 git 层

DSH 从 GitHub 安装插件走 `pnpm add <git spec>` → git clone，`github:owner/repo` 与仓库 URL
被判定为 git 类型，**不经过 npm 源**。界面的「安装源」下拉通过 pnpm `--registry` 传递，只影响 npm 包。
pnpm 的父环境经过清洗（剔除敏感键与 DSH_ 前缀变量），环境变量注入不可靠；HOME 保留，
因此全局 git 配置是唯一稳定的落点。

做法：写 `url.<代理>https://<host>/.insteadOf https://<host>/`，之后任何
`git clone https://github.com/...` 都被无痕重写到代理，原始地址不用改。

**双端都必须带协议**：git 按字符串前缀匹配目标 URL，`insteadOf` 写成裸主机（`github.com/`）
匹配不到 `https://github.com/...`，重写不生效且无报错——表现为直连超时，容易被误判成代理不可用。

候选清单外置在 `lib/core/github-mirror/candidates.json`，随仓库入库：

```json
{
  "version": 1,
  "candidates": [
    { "mirror": "https://example.invalid/", "hosts": ["github.com"], "disabled": false,
      "failures": 0, "lastOkAt": null, "lastError": null, "lastCheckedAt": null }
  ]
}
```

- `mirror` 必须以 `/` 结尾，工具会自动补齐。
- 显式传入的代理地址自动并入清单；探测成功清零失败计数，失败累加，满 3 次置 `disabled`，`probe` 可恢复。
- `clear` 只删指向受管站点（默认 `github.com`）的 insteadOf 规则，不动其它 git 配置。

## 三、minihost 与 preview 的模拟链路

`minihost` 是后端模拟，`preview` 是前端模拟，通过 `serve` 的 `backend` 参数串成一条链路，
全程不碰真实后端。`backend` 也可指向真实后端，此时是「前端模拟 + 真实后端」。

实现要点：

- **路由匹配只看路径**：`/api/x?y=1` 按 `/api/x` 匹配，query 原样交给 handler。
  早期实现拿含 query 的完整 URL 比对，任何带参数的接口都会 404。
- **默认隔离 DSH_HOME**：子进程的 `DSH_HOME` 指向 `.minihost/home-<port>`，避免插件写脏真实会话与附件库；
  依赖解析用 `--deps` 补回真实 profile 的 node_modules。需要贴近真实环境时用 `env` 覆盖。
- **服务注入**：插件接线依赖 `storageDomain` / `sessions` 等真实服务时，用 `services` 指向一个模块，
  该模块默认导出服务对象或返回服务对象的函数，注入项覆盖同名默认服务。
- 内置宽容桩：`webServer` / `tools` / `storageDomain` / `sessions` / `llm`，只保证调用不报错、不返回真实数据。
  `llm` 垫片只做三件事：记录 `registerAdapter` 收到的 providerIds（启动日志输出一行「llm 垫片：已注册适配器 …」便于验收自证）、
  `resolveModelInfo` / `listModels` 返回最小结构、未列出的方法一律 async noop。它**不转发请求、不解析模型**，不能用来验真实推理链路。
- 服务按 cordis 语义同时挂成 `ctx` 属性：插件既可以用 `ctx.get("llm")`，也可以直接写 `ctx.llm`；
  `ctx.effect(fn)` 会立即执行 `fn` 并把返回值当 disposer——插件普遍在 effect 里做路由注册，当成 noop 会导致「apply 成功但全 404」。
- 预览页内置错误面板：捕获运行时错误与未处理的 Promise 拒绝，渲染在页面顶部。
- `serve` 省略 `backend` 时沿用台账里最近一次存活的 minihost 实例，并在返回值里给出 `backendSource`；
  自动接入也要可追溯，避免静默连错实例。

## 四、ui_check 的能力边界

解析 `lib/client.js` 的 React 元素调用，产出 HTML 骨架页与 JSON 控件清单。

| 问题 | 能否回答 |
| --- | --- |
| 代码里声明了哪些控件、层级、className、文本 | 能，带来源行号 |
| 哪个插槽注册了、渲染的是哪个组件 | 能；组件在文件内定义时还会展开该组件的 UI |
| 条件分支 / 逻辑与里的元素 | 能，收进 `conditional` 子树，不漏报 |
| 运行时到底渲染出来没有（TDZ、条件为 false、hooks 报错、map 空数组） | 不能 |
| 真实外观（主题 CSS 变量、宿主布局约束） | 不能，只能用内联样式近似 |

它是静态骨架，不是渲染检查。清单里控件的 `visible` 恒为 `null`，留给将来的渲染探针填
true/false——两者共用同一份格式，可直接 diff 出「声明了但没渲染」的控件。

## 五、verify_plugin 的六段诊断

| 症状 | 检查段 | 判定依据 |
| --- | --- | --- |
| 装了但不激活、apply 没执行 | `activation` | profile 的依赖、bundle 列表、离线组合出的 loader 行，缺哪项报哪项 |
| 服务拿不到、路由 404 | `inject` | 声明的服务名与安装里实际存在的比对，拼错给近似建议 |
| import 失败、依赖找不到 | `deps` | 在目标 profile 的 node_modules 与 Node 解析里逐个试；`file:` 路径失效单独报 |
| UI 空白、控件没出来 | `client` + `ui` | 有 `dsh.client` 就必须有 `lib/client.js` 且走模块加载器；骨架 controls=0 直接判失败 |
| 改了代码没生效 | `hmr` | 读 profile 的 hmr 配置，判断插件路径是否在 watch 范围 |
| 同步后宿主读不到 | `sync_plugin` 的 `permissions` / `readable` | 写盘后对齐权限与属主，再逐个检查可读 |

激活诊断是离线组合（profile 的 patch 加上各 bundle 的 patch），不启动宿主；
运行期真实装配仍以宿主日志为准。工具本身只做静态分析，不 import 被验证插件。

## 六、DSH 插件规则（11 条）

规则有独立实现，判定口径与提交审计一致：

| 规则 | 严重度 | 判定 |
| --- | --- | --- |
| `dsh/import-bare-cordis` | error | 裸名导入 cordis |
| `dsh/import-bare-schemastery` | error | 裸名导入 schemastery |
| `dsh/tool-render-empty-body` | error | render 空实现或返回 null/undefined |
| `dsh/client-node-builtin-require` | error | client 半部 require Node 内置模块 |
| `dsh/schema-secret-field-role` | warning | token/secret/apiKey 字段缺 `role('secret')` |
| `dsh/patch-insert-unique-id` | warning | insert 行 id 与按 id 覆盖行重复 |
| `dsh/client-module-loader-id` | warning | client 入口未走模块加载器 |
| `dsh/ctx-undeclared-property-read` | blocker | 读 ctx 上已知的错误字段（注释行豁免） |
| `dsh/ctx-service-not-injected` | blocker | 访问 ctx.<服务> 但 inject 未声明（只查插件入口 + 已知服务名） |
| `dsh/plugin-default-export-hides-inject` | blocker | 入口同时有 `export default` 与命名 inject/apply |
| `dsh/host-api-guessed-fallback-chain` | error | 用猜测的 API 兜底链 |

匹配前先遮蔽注释与字符串内容（保持行号不变），只对真实代码匹配——
否则规则说明里写出的违规写法会触发规则自身。需要字符串内容的规则（模块名类）
先确认结构再回原文核对模块名。规则定义文件本身不参与扫描。

后两条需要**跨行读 `export const inject = [...]`**，纯逐行正则做不到，
因此提交审计侧用脚本扩展 `scripts/audit-ext/dsh-inject-declarations.mjs` 承载（不是 YAML 规则）；
本插件的 `lib/core/verify-plugin/dsh-rules.mjs` 是独立实现，判定口径与之一致（契约 C-114）。

`dsh/ctx-service-not-injected` 有两条保守边界，宁可漏报也不误报：
只检查**插件入口文件**（有 `export function apply` 或 `export const inject`），
且只报**已知 cordis 服务名**——`ctx` 是极常见的参数名（HTTP 请求、工具上下文、遍历累加器都叫 ctx）。

## 七、patch_cifs_write 改了什么

CIFS/SMB 不实现 POSIX chmod。官方原子写入流程是
`mkdir 临时目录 → chmod → open → chmod → write → fsync → (可选) chmod → rename`，
第二步就抛 `EPERM`，文件其实还没写进去。

补丁把三处 chmod 包成「尽力而为」：只吞 EPERM / ENOTSUP / EOPNOTSUPP，
EACCES / ENOENT / EIO 等照常抛；rename 与原子性完全不动。

- 补丁目标是套件安装目录，宿主升级会覆盖，升级后重跑 `apply` 即可（幂等）。
- 打完需重启宿主才生效（模块已在进程缓存里）。
- `revert` 从最新备份还原。

## 八、test_env 环境根优先级

参数 `root` > 环境变量 `DSH_TEST_ENV_ROOT` > 插件配置 `config.json` 的 `testEnvRoot` >
按 `DSH_WORKSPACE` / `DSH_HOME` 上一级的「工作区」推算。不写死路径，部署方按配置决定位置。

## 九、quick_command 的执行细节

- 定义存 `<DSH_HOME>/useful-tools/quick-commands.json`，无内置预置，文件不存在时是空表。
- `run` 只执行已定义的命令；同时传 `command` 时先写入 JSON（新增或更新）再执行，不是临时执行。
- `cwd` 缺省空 = 沿用宿主进程的 cwd（不一定是当前工作区）；传了会校验存在且是目录并解析成绝对路径。
- 执行走 `bash -c`（Windows `cmd /c`），默认超时 60 秒，stdout/stderr 各截断 20000 字符。

## 十、github_download 的通道选择与接管边界

### 被拦的是哪个域

`github.com/<owner>/<repo>/releases/download/<tag>/<file>` 本身不存文件，它 302 到
`release-assets.githubusercontent.com`（旧版是 `objects.githubusercontent.com`）。
本机实测：这个落地域 TLS 握手阶段被阻断，表现为连接挂住直到超时（不是 DNS 失败——
指定 CloudFront IP 直连同样不通），而 `api.github.com`、`codeload.github.com`、
`raw.githubusercontent.com` 都正常。

所以「换个 IP / 改 hosts」这类做法无效，被拦的是 SNI 而不是解析结果。

### 镜像前缀为什么能绕

公共镜像提供**前缀模式**：把完整原始 URL 拼在镜像地址后面，
`https://ghfast.top/https://github.com/...`。取文件的动作发生在镜像服务器侧，
本机全程只跟镜像站通信，不需要碰被拦的域——这跟 HTTP 代理不是一回事，
镜像站不理解 `CONNECT`，它只做「拿到路径里的 URL 再去取」。

### 通道选择逻辑

```
channel=auto（缺省）
  ├─ 探测直连（HEAD + follow 重定向，超时 4s）
  │    ├─ 通 → 直连下载（raw / archive 属于这一类，省一次镜像中转）
  │    └─ 不通 → 按候选清单轮换镜像
  └─ 每个镜像下载成功/失败都回写 candidates.json（连续失败 3 次自动停用）
```

`channel=direct` / `channel=mirror` 跳过决策，只走单一路径。

两个实现细节值得记：

- **探测镜像时拿到响应头就断 body**。实测 `ghfast.top` 不透传 `Range`，用
  `Range: bytes=0-0` 探测会返回整个文件，探测就变成一次真下载。
- **失败必须删半截文件**。文件存在且非零会被后续步骤当成「下载成功」，
  这个状态比「没有文件」更难排查。

### 接管边界

| 层次 | 能否接管 | 原因 |
| --- | --- | --- |
| 工具层 | 能 | 调用方只给 URL，插件内部选通道 |
| shell 层 | 只能显式调用 | AI 用 `bash -c` 执行命令时不加载 shell rc，函数别名管不到 |
| 全局拦截 | 不能 | 阻断在 TLS 层；镜像不是标准代理，只有 MITM（自签 CA + 全局信任）能改写 |

想把「任意 curl 都自动走镜像」做成全局，只能上 MITM 代理，代价是给整机装一套
根证书、多一个常驻进程，且一旦证书轮换失败所有 HTTPS 一起挂——收益与风险不成比例，
所以不做。真正需要批量下载的场景，用 CI 中转更稳。

## 十一、sync_plugin 的三种目标与上游差异算法

### files 字段只列变动文件

同步结果里的 `files` 现在只含「与目标内容有差异（或目标缺失）」的文件，
全量口径放 `totalCount`，一致数放 `unchangedCount`，`changedCount` 与 `files.length` 对齐。
判定仍由 `syncOneFile` 逐文件比内容得出（`fileContentEqual`），dryRun 与真写共用同一条路径——
预演时也能看出「会改哪几个」。

### target 参数与加载源

`target` 给了就直接用它（校验存在且是目录），省略则沿用 DSH_HOME → `local-plugins/<插件名>` 的旧行为。
这条参数是上游模式的地基：**装机版依赖的实际加载源往往不是 local-plugins**。
实测本机 `dsh-live-compact` 在 profile 的 package.json 里声明成 `github:MerkyorLynn/dsh-live-compact`，
pnpm 解析出的依赖落在 `node_modules/<插件名>` 且是真实目录，`local-plugins/` 下根本没有它——
只认 local-plugins 的旧逻辑对这类插件无能为力。

因此 `profileDir` 只在路径形如 `<profile>/local-plugins/<插件>` 时才推导出来，
其它形态（node_modules 直装）置空，不做「猜一个 profile 目录」的事。
显式 target 写错目录等于往别人的运行时代码里灌文件，宁可拒绝也不猜。

### 上游更新靠 git blob sha，零下载算差异

`api.github.com` 的 `git/trees/<ref>?recursive=1` 一次带回全仓每个文件的 blob sha。
本地文件自算 `sha1("blob <字节数>\0" + 内容)` 就能和它逐一对齐——
于是**不下任何文件就能精确知道哪些变了、哪些是新增、哪些本地多余**。

实测对照（1.0.5 装机目录 vs main 分支）

| 判定 | 结果 |
| --- | --- |
| 变动 | README.md / index.js / package.json / plan.js / shadow.js / shell.js |
| 新增 | raw.js / shadow-search.js |
| 一致 | 5 |
| 本地多余 | 0 |

拿到差异后才只下载这 8 个文件，每个都用 blob sha 校验，
镜像给脏内容会当场判失败而不是写进去。

### 白名单决定「哪些远端文件该装」

远端仓库里有 docs/ 与 test/（合计 1.2 MB 图片与测试），装进插件目录毫无意义。
判定按远端 `package.json` 的 `files` 字段做最小语义实现，与 npm pack 对齐——
精确文件、目录（含其下全部）、结尾斜杠目录、`!` 否定；顶层 package.json / README / LICENSE / CHANGELOG 始终包含。
glob 模式不支持（npm 那套 minmatch 语义不是几行能覆盖的），命中不了的如实报告而不猜。
上表的新增文件正是靠这条被筛出来的——`raw.js` 与 `shadow-search.js` 都在 `files` 里，
而 docs 与 test 全部落选。

### 覆盖前的三条安全线

- 缺省 dryRun，`write: true` 才动盘（与本地同步同一口径）。
- 先把**全部内容取齐并校验通过**再落盘；任一文件取不到就整体不写，避免半新半旧。
- 真写前把被覆盖的旧文件按相对路径备份到 `<DSH_HOME>/useful-tools/upstream-backup/<插件>-<时间戳>/`，
  更新记录写 `<DSH_HOME>/useful-tools/upstream-records/<插件>.json`（headSha 加每个文件的 sha，供「生效没」核验）。

单次要写的文件数超过 50 直接拒绝——多半是 target 指错了目录（比如指到一个空目录，
于是全部远端文件都算「新增」），这时该停下来核对而不是继续。

### 覆盖完要重启

`node_modules` 装载源不在 hmr 监视范围（chokidar 的默认 ignored 含 `node_modules/**`），
覆盖后必须重启宿主才生效；`local-plugins` 布局则热重载即可。
返回值里的 `restartNote` 就是按这个事实给的。

### 显式 target 的插件名防呆

`target` 放开「任意目录」后，「拿 A 插件源码覆盖 B 插件安装位置」从不可能变成一次手滑就能触发。
真实诱因是**宿主运行态闭包陈旧**——插件代码改了、部署副本同步了，
但宿主进程内存里 `runSync` 还是启动时 import 的旧实现（工具描述走 `useful_tools` 动态扫描所以是新的，
`run` 链却是旧的）。旧实现认识 `target` 却不认识 `fromGithub`，
于是「更新 live-compact」的意图被静默降级成「把 useful-tools 的 63 个文件同步进 live-compact 目录」，
只差一个 `write: true` 就会把那个插件覆盖坏。

门禁：显式 target + 源与目标都能读到 `package.json.name` + 两个名字不同 ⇒ 拒绝，
要放行必须显式 `allowMismatch: true`。目标目录没有 package.json（空目录、或装机版裸文件被删过）时不拦——
判据是「两边名字都在且冲突」，宁可对已知冲突硬拦，也不对未知形态瞎猜。

顺带说明部署一致性为何重要：`sync_plugin` 写对文件只是**磁盘**一致；
要让**运行态**也一致得靠 hmr 命中（`node_modules/<插件>` 是软链指向 `local-plugins/<插件>` 时 realpath 相同才热重载）。
硬链接双副本或纯 node_modules 装载源，改代码后不重启宿主就仍是旧闭包——
这正是上面那次事故的土壤，所以防呆不能只靠「记得重启」，必须在代码里挡住。
